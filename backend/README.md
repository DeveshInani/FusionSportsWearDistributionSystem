# School Uniform Store API

FastAPI, SQLAlchemy and MySQL (or SQLite for a quick local run).

## Run locally

SQLite is the default. For MySQL:

1. Use the MySQL database provided by your host, or create one if needed.
2. Copy `.env.example` to `.env` in this directory.
3. Set `DATABASE_URL` to your connection:

   ```dotenv
   DATABASE_URL=mysql+pymysql://avnadmin:REPLACE_WITH_DATABASE_PASSWORD@mysql-1b2a95ca-sportswearsolutionfusion.d.aivencloud.com:25138/defaultdb?charset=utf8mb4
   DATABASE_SSL_REQUIRED=true
   ```

   URL-encode special characters in the username or password. When TLS is
   required, the API verifies the database certificate and hostname. Set
   `DATABASE_SSL_CA` to the provider CA file if it is not available in the
   system trust store. For the provided Aiven database, the project CA is
   stored at `backend\certs\aiven-ca.pem`.
4. Set `SECRET_KEY` to a private random value of at least 32 characters and
   configure `BOOTSTRAP_ADMIN_EMAIL` and `BOOTSTRAP_ADMIN_PASSWORD`. The admin
   password must be at least 16 characters. The configured password is applied
   to that admin account at startup, so keep these values stable and private.
   Never reuse the example values or commit `.env`.
5. Install and start the API from this directory:

   ```powershell
   python -m pip install -r requirements.txt
   python -m uvicorn app.main:app --reload
   ```

The API applies pending migrations on startup, then seeds the demo roster and
catalog. Existing databases created by an earlier version are recognized and
baselined before the compatibility migration runs. Pillow is used to validate,
resize and re-encode admin-uploaded product and school images; uploads are
limited to 5 MiB and stored under `backend\uploads`.
When the migration converts legacy shared product stock to per-school stock,
the remaining quantity is distributed across existing school catalog entries
without increasing the total available inventory.

To apply migrations manually to a new database, run:

```powershell
python -m alembic upgrade head
```

Create future migrations after changing SQLAlchemy models:

```powershell
python -m alembic revision --autogenerate -m "describe schema change"
python -m alembic upgrade head
```

Review autogenerated migrations before applying them. `alembic current` shows
the database revision, and `alembic history` lists available migrations. Start
the API once before manually running migration commands against an existing
pre-Alembic database so it can baseline that schema first.

## Optional order email delivery

Without SMTP settings, order email messages are recorded as `simulated` in the
admin email log. To deliver real email, configure these values in `backend\.env`:

```dotenv
SMTP_HOST=smtp.example.com
SMTP_PORT=587
SMTP_USERNAME=your-smtp-user
SMTP_PASSWORD=your-smtp-password
SMTP_FROM_EMAIL=uniform-store@example.com
SMTP_USE_TLS=true
ADMIN_NOTIFICATION_EMAIL=store-admin@example.com
```

Email is attempted for order placement, successful/failed payments,
cancellations, student modifications and fulfillment status updates. Delivery
failures are recorded in the admin email log; they do not roll back a saved
order. Use a provider-specific app password or SMTP credential and do not
commit `.env`.

## School administration and delivery

Sign in with the configured admin account and open **Schools & catalog** to:

1. Create a school with its address, optional photo, and grade/section setup.
   Use the field-wise class and section form, or bulk upload/paste CSV rows
   with `Grade,Section` columns. Ranges such as `1-12: A, B` are also accepted.
2. Add student roster entries with separate name, class, section, and roll
   number fields, or bulk upload/paste CSV rows with
   `Name,Grade,Section,Roll Number` columns. Registration remains restricted
   to exact school roster matches and each roll number can only be claimed once.
3. Publish products for a selected school with category, audience, image,
   sizes, per-size prices, and per-school stock. Inventory edits are reflected
   immediately in that school's student catalog.

At checkout, delivery requires a street address, area, city, and postal code.
Students can enter the address manually and optionally share browser GPS
coordinates after pressing **Use my location**. Coordinates are not sent to a
mapping provider; when shared, they are stored with the order and shown to the
student and store admin. Pickup orders do not store delivery coordinates.

## POC journey

1. Register or sign in. Registration requires a matching roster entry.
2. Browse the catalog scoped to the student's verified school.
3. Add product sizes and quantities; the API validates current stock.
4. Review a server-calculated quote: subtotal, 5% demo tax, delivery fee and
   total. Pickup has no delivery fee.
5. Place an order:
   - UPI and net banking show a simulated success/failure step.
   - Cash at store stays unpaid until the cashier confirms it in the dashboard.
6. View the order number, PDF demo invoice, notification log and estimated
   delivery or pickup date.
7. Track the order timeline:
   - Every order starts as `awaiting_payment` (the order is received). UPI and
     net-banking failures release reserved stock and can be retried only if
     stock is available again. Students may also cancel before preparation.
   - Cash orders remain `awaiting_payment` until the cashier confirms payment;
     they then move to `processing`.
   - Students may change items while payment is pending or while a paid order
     is still `processing`. The server checks catalog eligibility and stock,
     then recalculates subtotal, 5% tax, delivery fee and total from current
     catalog prices. A changed unpaid quote updates the amount due. A paid
     order records the exact additional charge or refund required; the order
     stays on hold until the adjustment succeeds. Failed adjustments can be
     retried or the order cancelled. For example, adding a â‚¹200 item to a
     â‚¹500 pickup subtotal makes the subtotal â‚¹700, tax â‚¹35 and amount due
     â‚¹735. Delivery orders also include the delivery fee in the server total.
   - Students may cancel an `awaiting_payment` or `processing` order. Stock is
     released once; unpaid orders are cancelled, while paid orders record a
     simulated refund for the amount actually paid. Orders cannot be edited
     or cancelled after preparation starts.
   - Admins confirm cash and progress paid orders through `preparing`, then

8. Admin sales analytics show daily orders, product rankings (including
   products with no sales), category/gender mix and order statuses. System
   health shows in-process RAM, CPU, request concurrency and latency metrics.

Payments and refunds remain simulated. SMTP email is optional and becomes real
only when configured; otherwise messages are logged as simulated.
